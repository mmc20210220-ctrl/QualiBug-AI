01 为什么是现在

系统改得越来越快，
有没有改坏却越来越难说清

企业软件系统正在被更快地改变——被人改、被自动化程序改、也被 AI Agent 改。变更速度提高了一个数量级，而「这次改动到底破坏了哪条业务规则」，依旧靠人去读需求、造数据、修脚本、猜回归范围、翻失败日志。

  • COST 01

    人工拆解需求

    把 PRD、接口文档、历史缺陷读成测试点，靠个人经验，无法沉淀。

  • COST 02

    人工维护数据

    测试数据造得慢、清得更慢，环境一脏，结论就不可信。

  • COST 03

    人工维护脚本

    界面一改、接口一改，脚本与定位器批量失效，维护吃掉全部收益。

  • COST 04

    人工判定回归范围

    影响面靠猜：多测浪费窗口，少测直接漏到生产。

  • COST 05

    人工分析日志

    失败原因分类、缺陷整理、复现步骤，仍然是纯手工劳动。

企业缺的不是又一个自动化脚本框架，
而是低成本地生成、维护与治理测试资产的能力。

— QualiBug AI 企业级落地方案 · 核心判断

02 行为空间

先把企业系统
变成一个可计算的空间

QualiBug 不从「写用例」开始，而是从建模开始。企业资料与运行时事实先被编译成 Behavior IR（行为中间表示），再由它推导出必须被验证的义务，最后编译成可以真正跑起来的实验。每一步都可追溯到来源，不允许凭空生成。

Input · 输入

企业已有的东西

  • 01产品与业务资料：PRD、业务规则、流程说明
  • 02接口与数据契约：API 文档、字段字典
  • 03角色与账号：用户角色、测试账号、权限矩阵
  • 04历史缺陷：过往真实问题与回归记录
  • 05运行时观测：真实请求与响应事实
Model · 行为空间

被映射成的坐标

  • A操作者（Actor）：谁在操作——人、程序，还是 AI Agent
  • S状态（State）：实体处在哪个业务状态
  • D数据（Data）：数据与实体之间的真实关系
  • R规则（Rule）：必须始终成立的业务不变量
  • T轨迹（Trajectory）：一次真实执行走过的路径
Output · 产出

可执行、可交付的资产

  • 01测试义务：这个系统必须被验证的性质
  • 02可执行实验：受治理的读写探针序列
  • 03证据链：before / after 观察与审计回执
  • 04正式缺陷：通过交付门禁、可复现的结论
  • 05发布判断：这次能不能放行
  1. 企业资料 + 运行时事实Materials + Runtime Facts
  2. 行为中间表示Behavior IR
  3. 测试义务Test Obligations
  4. 可执行实验Executable Experiments
  5. 证据链Evidence

DEPTH · 深度

多步业务因果

不是「单个请求返回 200 就算通过」。QualiBug 推理跨实体状态、长周期生命周期、以及多步操作串起来之后本应守恒的量。

BREADTH · 广度

不靠固定检测器清单

发现由业务不变量与系统空间坐标变化驱动。缺陷类型只是事后用于报告和回归的标签，不是发现能力的上限。

NEUTRAL · 中立

不硬编码任何客户业务

行业中立是硬约束：不允许把任何一个客户、任何一个行业的业务规则写进检测逻辑。业务规则只能来自你提供的资料，不能来自我们预置的行业模板。

03 核心能力

一条从资料到发布决策的完整主线

六个能力构成一条闭环，而不是六个互相独立的功能模块。

01 / MODELING

行为空间建模

把企业资料与接口文档编译成行为中间表示（Behavior IR），形成操作者、状态、数据、规则的统一表示，作为后续一切推导的唯一事实来源。

02 / OBLIGATION

测试义务编译

由不变量推导出「必须被验证的性质」。每条义务都必须挂接到来源声明与具体操作上——没有来源，就不会被生成。

03 / EXPERIMENT

可执行实验编排

义务被编译成实验：固定装置 DAG、控制组与实验组、受治理请求序列。绑定不完整的实验会显式标记为 BLOCKED，而不是假装通过。

04 / EVIDENCE

四段式证据管道

原始探针证据 → 归一化运行时证据 → 语义验证证据 → 业务发现契约。每一段都可回溯，中间不允许出现推断。

05 / GATE

客户交付门禁

只有通过正式门禁的结果才会进入客户视野。未通过的会留在「内部线索」里，并明确写出缺了什么——不塞进报告凑数。

06 / KNOWLEDGE

企业知识统一接入

企业资料被沉淀为可复用的知识资产，跨项目、跨版本持续积累，而不是每次测试都从零开始读一遍文档。

04 证据链

一个缺陷，
凭什么值得你去修

AI 报告最贵的成本不是生成，是核实。所以 QualiBug 把证据做成一条有形状的管道：每一段都留痕，每一个结论都必须指回真实执行过的请求与观察。

  1. 1RAW PROBE EVIDENCE

    原始探针证据

    真实发出的请求、真实收到的响应、真实发生的时间点，原样留存。

  2. 2NORMALIZED RUNTIME

    归一化运行时证据

    把原始观测规整成统一结构，可比较、可回放、可作为下一步判定的输入。

  3. 3SEMANTIC VERIFICATION

    语义验证证据

    用断言与契约判定：这次观测到的行为，是否违反了那条业务不变量。

  4. 4BUSINESS FINDING

    业务发现契约

    形成一个可交付的缺陷结论：违反了什么、在哪一步、怎么复现。

不推断，只观测

不得推断请求体、凭据、业务规则、表名 / SQL 或影响结论。没有观测到的东西，产品不会替你写出来。

合成指引 ≠ 证据

格式化的操作指引可以生成，但会被明确标注，且永远不能替代真实执行证据，也不能通过客户交付门禁。

每次写入都有回执

受治理沙箱中的每次写操作，都会产出 before / after 观察、清理结果与审计回执。清理失败会被如实保留。

05 交付门禁

宁可少给一条，
也不给一条要你自己去验的

客户交付门禁决定哪些结论可以送到你面前。未通过的不会被丢弃，而是连同缺失原因一起对你可见。

  • 没有真实执行证据的缺陷，不会被交付

    这是产品的硬约束，不是一个可以按项目放宽的配置项。

  • 未通过的线索也对你可见

    它们进入「内部线索」，并写清缺了哪一环。你能看到系统在想什么，而不是只看到一份筛选后的结论。

  • 空结果不等于系统没问题

    如果一次运行的义务全部被阻塞，它会显式标记为 BLOCKED。产品不会把「没跑成」包装成「很干净」。

  • 内部漏斗计数不会被包装成召回率

    候选数、确认数、验证数只用于诊断转化损失，永远不会作为商业能力指标对外报出。

06 执行治理与安全

让企业敢把它接进来

一个会真实发请求、会真实写数据的系统，必须先证明自己是安全的。 QualiBug 的默认姿态是失败即关闭（fail-closed）：说不清楚的环境，一律不写。

只对显式声明的非生产目标写入

生产环境与「类型未知」的环境，写操作一律拒绝。localhost 或某个环境名字，永远不构成写入安全的证明。

受治理沙箱与清理回执

每次写入都在治理沙箱中进行，产出 before / after 观察、清理结果与审计回执；清理失败会被如实记录，不会被抹掉。

操作员级熔断开关

一个开关即可全局停写：所有写操作在请求发出之前被阻断，而不是发完再回滚。权限在你的运维手里，不在我们这里。

完全私有化部署

部署在你的企业内网，默认只监听本机、不对外开放。需要对外访问必须由你显式开启，并置于企业自己的反向代理之后。

凭据静态加密，缺密钥拒绝启动

凭据加密主密钥缺失时，服务直接 fail-closed 拒绝启动，而不是降级成明文继续跑。

一键交付现场自检

内置只读诊断，进场一条命令就能判断环境是否满足运行条件，不靠现场调试碰运气。

数据出网边界

产品私有化部署，
但推理模型的位置由你决定

QualiBug 的服务、运行状态与证据数据全部落在你的企业内网，默认只监听本机、不对外开放。但发现能力依赖大模型推理，而模型接在哪里，决定了内容是否出网。

这个选择在部署时由你做，产品不替你决定，也不会把两种情况混为一谈、笼统说成「数据不出企业网」。

  • 接企业内部模型（自建或私有化大模型服务）——全链路不出企业网络。
  • 接外部模型供应商——送去推理的资料内容会离开企业网络，抵达该供应商。

如果贵司的合规要求是数据零出网，请在部署阶段就选择内部模型接入，我们配合完成对接。

07 发现能力与口径

十类高价值业务缺陷，
带证据、可复现地交付

每一类都对应一种真实的业务损失，而这十类只是起点——缺陷类型体系是开放的。当期覆盖矩阵随交付文档逐项确认，你不需要靠试探来发现产品的边界。

  • 01
    越权访问低权限角色能读到或改掉不属于它的数据
  • 02
    租户 / 项目隔离失效一方的操作影响到另一方的数据或额度
  • 03
    状态非法流转跳过必经环节，或已终结的单据被再次变更
  • 04
    数量与金额不守恒多步操作串起来之后，前后账目对不平
  • 05
    幂等失效重复提交产生了重复的业务后果
  • 06
    并发竞态同时操作导致超发、重复扣减或互相覆盖
  • 07
    校验缺口越界与非法输入被接受，落库成脏数据
  • 08
    可见性口径不一致列表、详情与导出对同一份数据给出不同结果
  • 09
    时序与时间窗到期未生效、超时未收敛、跨时段行为不一致
  • 10
    隐私字段泄漏敏感字段出现在不该出现的接口或导出里

每一类都走完整链路：来源可追溯的测试义务 → 受治理实验 → 真实执行观测 → 断言与契约判定 → 客户交付门禁。没有走完这条链路的，不会出现在交给你的结果里。

开放的缺陷类型体系

这十类是典型，不是清单的上限。发现由业务不变量与行为空间坐标变化驱动，不受固定检测器清单限制——任何有证据的不变量违反都在范围内，包括还没有名字的缺陷类型。观测面（API、数据库、UI、消息链、性能……）沿产品路线持续扩展，每打通一层，都进入同一条证据与交付门禁链路。

各观测面的当期覆盖矩阵随交付文档提供，在技术评估中逐项确认——官网介绍能力体系，交付口径以文档为准。

交付的是结论

不是一份等你去核实的报告

塞满「疑似问题」的报告，成本会转嫁给你的测试与研发逐条核实。可复现的少数结论，比不可核实的多数噪音更值钱。

交付口径书面化

口径写在合同前，不在验收后

当期覆盖矩阵在技术评估中逐项书面确认。你的架构决策、排期与验收标准，可以直接建立在确定的口径上，而不是等交付时再对齐。

标准只升不降

能力增长，不以放松标准为代价

新观测面上线后走的仍是同一条证据链与交付门禁。发现得更多，从来不意味着交付得更松。

08 落地路径

从接入到发布决策的
五个步骤

01

登记项目、服务地址、鉴权方式与数据库配置，并显式声明每个目标的环境类型。环境类型是一个必填事实——它决定了系统是否允许写入。

02

03

发起发现运行 ENTERPRISE CAMPAIGNS

统一运行中心：发起标准扫描或受控执行。运行权威在创建前冻结，运行中不允许切换——保证结果可复现。

04

查看结果与证据 FINDINGS · EVIDENCE CHAIN

逐条查看正式缺陷与其完整证据链；同时可以查看未通过门禁的内部线索，以及它们各自缺失的环节。

05

发布门禁判断 RELEASE GATE

把发现结果接进发布决策：这次变更是否达到交付就绪，由证据而不是由感觉决定。

10 愿景

成为企业系统运行的独立验证层

成为企业系统运行的
独立验证层

  • 多系统
  • 多服务
  • 多数据库
  • 多消息链
  • 人 / 程序 / AI Agent
  • 全行业中立

我们的做法是：先把观测面一层层打通，再宣称对应的能力 —— 而不是先把话说满。

在 AI 时代，企业系统会越来越多地由程序和 AI Agent 操作。操作方可以不断更换，但验证层不能缺席—— 而且它不能属于任何一个操作方。

QualiBug AI 的长期方向，是成为这一层独立验证层：不替系统做决定，只对可观测的行为负责；不假设操作者是谁，把操作者身份当作验证的输入，而不是内置在检测逻辑里的假设。验证能力本身也将以 SaaS 形态云端交付，并通过 API、CLI 与 Agent-to-Agent 接口，开放给程序与企业智能体直接调用。

目标覆盖全行业、全系统类型：ERP、MES、WMS、CRM、财务、供应链、医疗、教育、多租户 SaaS —— 没有任何一项能力被限定在某个行业里，也没有任何一个行业被排除在外。

11 常见问题

你大概率会问的几件事

它会不会碰我的生产环境？
不会。自动读写探针只对显式声明为非生产的目标执行；生产环境与类型未知的环境对写操作一律 fail-closed。此外还有一个由你的运维掌握的全局停写开关，打开后所有写操作会在请求发出之前被阻断。环境类型是必填事实，不会因为地址是 localhost 就被默认成安全。
这是不是一个扫描器 / 爬虫？
不是。QualiBug 不做全站遍历，也不做规则库匹配式扫描。它先把系统建模成行为空间，再由业务不变量推导出必须验证的义务，然后编译成受治理的实验去执行。产品语义中的 Bug 指的是「观察到的行为」与「期望行为」之间可证据化复现的偏差——与昆虫、爬虫、抓取无关。
需要把源代码给你们吗？
不需要。产品消费的是可见的企业资料、配置的接口端点、声明的测试角色与运行时观测事实。它以黑盒方式工作在你的非生产环境上。
数据会不会离开我们的网络？
分两层看，我们不把它们混为一谈。产品自身是完全私有化的：本地或 Docker 部署在企业内网，容器默认只映射到 127.0.0.1，对外暴露需要显式开启并置于企业反向代理之后；凭据在静态存储时加密，加密主密钥缺失时服务直接拒绝启动。模型侧取决于你的选择：接企业内部模型则全链路不出网；接外部模型供应商，则送去推理的资料内容会离开企业网络。如果贵司要求数据零出网，请在部署阶段就选择内部模型接入。详见 数据出网边界。
和我们现有的自动化测试框架冲突吗？
不冲突，定位不同。现有框架回答的是「我写好的用例有没有通过」；QualiBug 回答的是「这个系统有哪些本该成立的业务性质，现在不成立了」。正式缺陷可以直接进入你既有的缺陷流程，发现结果也可以接进 CI 作为发布门禁的一部分。
为什么你们不公布召回率 / 精确率数字？
因为这些数字还没有被外部可验证地测量，而我们不公布无法核验的数字。产品内部有一条硬规则：外部质量指标在拿到可验证的评测回执之前必须保持 NOT_MEASURED，内部候选数、确认数、漏斗计数不得被包装成召回率或商业能力。把这条规则写进官网，是因为它同样约束我们在销售场景里的表述。
一次运行没发现缺陷，是不是说明系统是干净的？
不能这样解读，产品本身也拒绝这样呈现。如果一次运行的测试义务全部被阻塞，它会显式标记为 BLOCKED 而不是「通过」。另外，各观测面的当期覆盖以交付文档为准；未纳入覆盖的观测面上没有结果，只代表未覆盖，不代表那里没有问题。
