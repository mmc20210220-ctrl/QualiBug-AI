# ContractFlow 产品需求文档（PRD）

**版本：** 1.0  
**系统类型：** 企业合同履约与付款审批系统  
**适用范围：** 多租户企业内部合同管理、预算控制和供应商付款

---

# 1. 产品目标

ContractFlow用于管理从合同起草到最终付款和关闭的完整生命周期。系统必须保证每笔付款有合法合同、已验收里程碑、有效发票、足够预算和完整审批链，并保留可审计证据。

核心价值：

- 防止未经审批的合同生效；
- 防止超预算、超合同、超里程碑付款；
- 防止重复付款；
- 防止跨租户、跨部门和越权操作；
- 保证合同、里程碑、发票、付款和预算之间一致；
- 支持取消、驳回和重新提交；
- 支持审计与事后追责。

---

# 2. 用户角色

| 角色 | 说明 | 核心权限 |
|---|---|---|
| requester | 合同发起人 | 创建和修改自己部门的草稿合同、提交审核 |
| project_manager | 项目负责人 | 提交里程碑验收、审批付款业务合理性 |
| legal | 法务 | 审核合同条款、批准或驳回法务审核 |
| finance | 财务 | 审批付款、执行付款、查看预算 |
| vendor | 供应商联系人 | 查看对外合同摘要、提交履约材料和发票 |
| auditor | 审计员 | 只读查看全租户业务数据和审计日志 |
| admin | 租户管理员 | 用户、部门、预算和全部业务管理 |

角色只在所属租户内有效。任何用户不得访问其他租户数据。

---

# 3. 核心实体

## 3.1 合同 Contract

合同字段包括合同编号、标题、供应商、部门、合同金额、币种、开始日期、结束日期、状态、已支付金额、内部备注和版本号。

合同状态：

```text
DRAFT
→ LEGAL_REVIEW
→ APPROVED
→ ACTIVE
→ COMPLETED
```

可选分支：

```text
LEGAL_REVIEW → REJECTED → DRAFT
DRAFT / LEGAL_REVIEW / APPROVED / ACTIVE → CANCELLED
```

约束：

- 合同金额必须大于0；
- 开始日期必须早于结束日期；
- 合同编号在同一租户内唯一；
- 草稿合同只有发起人或管理员可修改；
- 合同提交审核前至少包含一个里程碑；
- 全部里程碑金额之和必须等于合同总金额；
- 法务批准后才能进入APPROVED；
- APPROVED合同由管理员或项目负责人激活；
- 激活时预留对应预算；
- 只有已激活合同才能提交履约和付款；
- 所有已验收里程碑均完成付款后才能完成合同；
- 已取消合同不能重新激活、付款或新增里程碑。

## 3.2 里程碑 Milestone

状态：

```text
PENDING → SUBMITTED → ACCEPTED
                    ↘ REJECTED → SUBMITTED
```

约束：

- 里程碑必须处于合同起止日期范围内；
- 里程碑金额必须大于0；
- 同一合同的里程碑金额总和必须等于合同金额；
- 只有ACTIVE合同允许提交履约材料；
- 供应商或项目负责人可提交履约材料；
- 只有项目负责人、合同发起人或管理员可验收；
- ACCEPTED里程碑不得重复验收；
- 验收记录每次状态变化只能生成一条；
- 被驳回后可重新提交，但必须增加提交版本。

## 3.3 发票 Invoice

约束：

- 发票必须关联同一租户、同一供应商和同一合同；
- 发票号在同一供应商内唯一；
- 发票金额、税额不得为负；
- 含税金额等于未税金额加税额；
- 发票日期不得晚于付款申请日期；
- 作废发票不得用于付款；
- 发票总额不得低于本次付款金额。

## 3.4 付款申请 Payment Request

状态：

```text
DRAFT
→ MANAGER_APPROVED
→ FINANCE_APPROVED
→ PAID
```

驳回分支：

```text
DRAFT / MANAGER_APPROVED / FINANCE_APPROVED → REJECTED
```

约束：

- 付款申请必须关联ACTIVE合同、ACCEPTED里程碑和有效发票；
- 付款金额必须大于0；
- 付款金额不得超过里程碑剩余可付金额；
- 同一发票累计付款不得超过发票含税金额；
- 同一合同累计付款不得超过合同总金额；
- 项目负责人完成业务审批后，财务才能审批；
- 财务审批后才能执行付款；
- PAID和REJECTED为终态；
- 执行付款必须支持幂等键；
- 相同幂等键重复调用必须返回同一付款结果，不得重复扣减预算；
- 付款成功后必须同时更新付款状态、预算、合同累计已付款金额和审计日志。

## 3.5 预算 Budget

预算按租户、部门、年度维护。

字段：

- `total_amount`：总预算；
- `available_amount`：可用预算；
- `reserved_amount`：合同已预留但未支付；
- `spent_amount`：已支付金额。

必须始终满足：

```text
total_amount = available_amount + reserved_amount + spent_amount
```

业务规则：

- 任何金额不得为负；
- 合同激活时：`available -= contract.total`，`reserved += contract.total`；
- 合同付款时：`reserved -= payment.amount`，`spent += payment.amount`；
- 合同取消时：未付款部分从reserved释放回available；
- 不允许激活超过可用预算的合同；
- 预算更新必须使用版本号或数据库锁避免并发超支。

# 4. 业务流程

## 4.1 合同创建与生效

1. requester创建合同草稿；
2. requester添加里程碑；
3. 系统验证里程碑合计等于合同金额；
4. requester提交法务审核；
5. legal批准或驳回；
6. APPROVED合同被激活；
7. 系统预留部门预算；
8. 记录审计日志。

## 4.2 履约验收

1. vendor或project_manager提交里程碑履约材料；
2. 系统将里程碑改为SUBMITTED；
3. project_manager验收或驳回；
4. ACCEPTED后生成唯一验收记录；
5. 已验收金额成为可申请付款额度。

## 4.3 付款

1. requester或project_manager为已验收里程碑创建付款申请；
2. 系统校验合同、里程碑、发票和剩余额度；
3. project_manager业务审批；
4. finance财务审批；
5. finance执行付款；
6. 系统原子更新付款申请、预算、合同累计付款；
7. 重复付款请求通过幂等键返回已有结果。

## 4.4 合同取消

1. 有权限用户取消合同；
2. 系统禁止对COMPLETED合同取消；
3. 已支付金额保持不变；
4. 未使用预留预算释放；
5. 所有未完成付款申请自动REJECTED；
6. 后续付款、履约和激活操作全部禁止。

## 4.5 合同完成

只有满足以下条件才能COMPLETED：

- 所有里程碑均ACCEPTED；
- 所有已验收金额均已支付；
- 没有DRAFT、MANAGER_APPROVED、FINANCE_APPROVED状态付款；
- 合同累计已付款金额等于合同总金额。

---

# 5. 并发与幂等

- 合同和预算更新携带`version`；
- 客户端更新时提交`If-Match-Version`；
- 版本不一致返回409；
- 支付执行必须提供`Idempotency-Key`；
- 同一租户内幂等键唯一；
- 并发激活合同不能导致预算变负；
- 并发付款不能超过里程碑或合同额度。

---

# 6. 安全与数据可见性

- 所有查询必须按tenant_id过滤；
- vendor只能看到对外字段，不能看到内部备注、预算和审批意见；
- requester只能修改自己创建的DRAFT合同；
- auditor只读；
- finance不能替代legal批准合同；
- project_manager不能执行付款；
- 普通用户不能查看全部租户审计日志。

---

# 7. 审计要求

以下操作必须记录：

- 合同创建、修改、提交、审核、激活、取消、完成；
- 里程碑提交、验收和驳回；
- 发票创建和作废；
- 付款创建、审批、支付和驳回；
- 预算预留、释放和支付；
- 管理员配置变更。

审计记录不可修改和删除，至少包含：操作者、租户、实体类型、实体ID、动作、前后状态、时间和请求关联ID。

---

# 8. 非功能需求

- 普通查询P95低于500ms；
- 关键写接口P95低于1.5s；
- API错误使用统一JSON结构；
- 所有金额使用两位小数；
- 时间使用UTC ISO-8601；
- 数据库事务失败必须整体回滚；
- 系统支持至少两个独立租户。
