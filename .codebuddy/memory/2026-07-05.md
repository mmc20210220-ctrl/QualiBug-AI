## 修复声明-证据矛盾误报（claim-evidence-consistency）

### 问题
用户发现 finding "超长email导致服务端500" 声称服务端返回 500，但实际 HAR 证据显示响应 201（成功），服务器正确处理了请求。这是误报——声称的异常没有发生。

### 根因
`_enforce_evidence_gate` 只检查证据完备度（有无预期/实际/API响应），不检查"finding 声称的异常"与"实际运行证据"是否一致。当 finding 标题说"服务端500"但实际响应 2xx 成功时，系统仍把它当作有效发现。

### 修复
`display_ready_formatter.py`：
1. 新增 `_check_claim_evidence_consistency(finding)` — 从标题/描述提取声称的 HTTP 错误码（4xx/5xx），与 HAR 实际响应状态码比对，声称错误但实际 2xx → 判定为矛盾
2. `_enforce_evidence_gate` 增加声明-证据一致性检查（对所有状态执行，不仅 reproduced），发现矛盾时降级为 `not_reproduced`

### 测试
5 个场景验证通过：声称500实际201→矛盾、声称500实际500→无矛盾、无声称码→无矛盾、risk_clue+矛盾→not_reproduced、无矛盾risk_clue保持不变

## Bug 累积 + 自动扫描收敛（cumulative-bugs-and-auto-scan）

### 问题
1. 每次点击运行检测后，bug 数据是当次的不是累计的——未修复的 bug 在下次扫描时消失了
2. 只有手动点击运行，没有自动运行+手动运行并存+收敛停止机制

### 根因
- `__main__.py:767` `_persist_scan_result` 用 `"w"` 覆盖写 `scan_result.json`
- `_build_command_center` 从 `scan_result.json` 读 findings，覆盖后历史发现丢失
- `findings` 表已有 `status='open'` 字段但 `_build_command_center` 不从 DB 读

### 修复

**功能1：Bug 累积（db_persistence.py + private_pilot_service.py）**：
1. `merge_findings_cumulative()` — 按 dedupe key(title+method+path) 合并，已存在的不覆盖 status，新发现的插入为 open
2. `get_cumulative_findings()` — 读累积 findings，默认只返回 open
3. `update_finding_status()` — 更新 finding 状态
4. `get_finding_stats()` — 返回 open/resolved/falsified/total 统计
5. `_handle_v12_scan` 改为调用 `merge_findings_cumulative`
6. `_build_command_center` 合并 DB 累积 findings 到 risks 列表
7. `_handle_replay` 根据复现结果更新 finding 状态（success=False→resolved）
8. command-center 返回新增 `cumulative_stats` 和 `continuous_state` 字段

**功能2：自动扫描+收敛停止（private_pilot_service.py）**：
1. 新增 `/api/v1/continuous/start` 和 `/api/v1/continuous/stop` 端点
2. `_continuous_scan_loop` 后台线程：按间隔运行 scan，每次后检查收敛
3. 收敛条件：连续3轮无新发现 + 覆盖率≥70%
4. 收敛后自动停止，上传新文档或手动 start 时恢复
5. 安全上限：最多20轮防止无限循环

### "Bug 货架"模型
Bug 像"货架上的商品"：发现后一直在货架上，新扫描不会拿走旧 bug。只有 replay 确认不再复现才标记 resolved 移除。未修复的 bug 永远保留。

### 测试验证
累积逻辑测试通过：Round1(3新)→Round2(A存在+B新+C/D保留=4open)→标记B resolved→3open+1resolved

### 注意
需要重启后端使改动生效。

## 扩展一致性检查：认证误报（auth-false-positive-check）

### 问题
finding "product双重提交" 声称幂等性问题，但 HAR 证据显示 POST /api/auth/login 返回 401 + {"error":"invalid credentials"}——这是登录端点正确拒绝无效凭证，与"product双重提交"完全无关。3个规则引擎都把401当"错误码"验证通过，误判为Bug。

### 根因
`_check_claim_evidence_consistency` 只检查状态码矛盾（声称5xx实际2xx）、响应体矛盾、状态标记矛盾，不检查：
- 401/403认证错误被误判为非认证类Bug
- 认证端点返回401是预期行为（系统正确拒绝无效凭证）

### 修复
`display_ready_formatter.py` `_check_claim_evidence_consistency` 增加两个检查维度：
4. **认证错误被误判为Bug**：401/403 + finding声称的不是认证类问题 → 矛盾（扫描器遇到认证墙）
5. **认证端点返回401是预期行为**：/auth/login等端点返回401 + 响应体含"invalid credentials"类 → 不构成Bug

### 通用性
- 401/403是标准HTTP状态码，非业务概念
- 认证端点路径模式(/auth/, /login, /signin, /token, /oauth)是HTTP标准约定
- 凭证拒绝关键词(invalid/incorrect/expired/credentials/password/token)是通用英文/中文
- 适用于任何行业的任何API

### 测试
用户报告的精确场景验证通过：2个矛盾检测到 → 降级为not_reproduced。既有36个测试无回归。
