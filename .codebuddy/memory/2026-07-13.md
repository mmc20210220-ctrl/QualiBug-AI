## Discovery 真实发现率优化（用户核心诉求）

用户提供基线数据后，定位了发现率低（baseline Recall 0.0534 / 7-of-131）的根因并落地一处精准修复。

### 数据驱动的瓶颈定位（用项目自身逻辑回放，非拍脑袋）
- 用 `customer_delivery_gate.customer_delivery_rejection_reasons` 回放 bound_write 后真实数据（findings=38 + candidate_findings=108）：146 条中仅 38 过门控，108 个候选几乎全被拒，其中 **96 个因 `BUG_STATUS_NOT_REPRODUCED` + `EVIDENCE_QUALITY_NOT_VALIDATED`**。结论：这些被拒候选绝大多数是噪声/假阳性，**门控是健康且严格的，放宽门控只会崩 precision（违反用户硬约束）**。因此 stage 9「证据链不足」不是真瓶颈。
- 真正瓶颈在 **触达（probe_selection 漏斗 632→181，丢弃 71%）**，对应 miss_diagnosis 的失败阶段分布 top=stage3（行为路径未触达，44 个）+ stage2/6。基线 `bug_reach_rate` 仅 49.6%（65/131 相关路径未被执行）。

### 实施改动
- 文件：`ai_test_asset_center/risk_based_probe_planner.py` 的 `_select_probes_by_budget`。
- 改动：在预算内加入 **GT-free 模块覆盖保底**——`_module_of(probe)` 提取 API 路径的业务资源段（如 `/api/orders/...`→`orders`），选择分两阶段：pass1 保证每模块至少 1 条探针，pass2 按原 priority 填满剩余预算。
- 原则符合：零成本（不改 `max_count`，baseline 已是 aggressive 上限 180）、全行业通用（仅基于 source-declared path，不碰 ground truth/分数/答案）、不虚增。
- 测试：`tests/test_select_probes_coverage_floor.py`；pytest 该文件 + 现有 `test_risk_based_probe_planner_validated_yield.py` 共 **7 passed**。
