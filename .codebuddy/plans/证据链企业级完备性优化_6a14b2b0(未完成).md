## 用户需求

对证据链进行全面排查和详细优化，使每条缺陷的证据完备、结构化、可审计，让企业用户一眼就能接受。

## 产品概述

证据链是 QualiBug 产品的核心卖点——把每条缺陷的发现过程拆解为可追溯的证据步骤（规则来源→接口请求→接口响应→数据库证据→日志线索→缺陷判定），按业务/测试/研发三个视角差异化展示，并可视化证据完备度。

## 核心功能

- 后端从 HAR/DB/文档/日志/复现等多源数据中提取结构化证据步骤，每步标注来源、时间戳、置信度
- 证据步骤支持 7 种类型（规则/接口请求/接口响应/数据库证据/日志线索/复现结果/缺陷判定），前端按类型差异化渲染
- 三视角差异化：业务视角只看规则+影响+判定；测试视角看请求+响应+复现；研发视角看全量+SQL+日志
- 证据完备度进度条：可视化已具备/缺失的证据类型，企业一眼知道还缺什么
- 去除 EvidenceTimeline 的 5 步截断限制，展示完整证据链

## Tech Stack

- 后端：Python 3.12+，`display_ready_formatter.py` 层重构（不修改 har_bridge/deep_verifier/replay_engine 输出结构）
- 前端：React 19 + TypeScript 5 + 自定义 CSS（无组件库，保持现有架构）
- 数据流：后端 display-ready JSON → 前端零加工纯渲染

## Implementation Approach

### 核心策略：在 formatter 层从现有字段提取结构化证据，不改数据源

当前 `_build_display_evidence_chain()` (L293-342) 生成 4-5 个固定文本步骤，大量真实数据被浪费。重构为**多源数据驱动的条件式证据链构建**——从 finding 已有字段（har_evidence/source_entity/sql_verify/trace_id/doc_refs 等）中提取结构化证据，每个步骤携带 timestamp/source/confidence/structured 元数据。

### EvidenceStep 新结构（后端 Python dict → 前端 TypeScript interface）

```python
# 后端新增字段（向后兼容，旧字段 label/content/detail 保留）
{
    "tag": "rule" | "api_request" | "api_response" | "db_evidence" | "log" | "replay" | "verdict",
    "label": str,           # 中文标签（如"接口请求""数据库证据"）
    "content": str,         # 主要内容摘要
    "detail": str,          # 补充说明
    "timestamp": str,       # 证据时间戳（如有）
    "source": str,          # 来源标识："HAR" | "DB" | "文档" | "日志" | "复现" | "系统"
    "confidence": float,    # 置信度 0-1
    "structured": dict | None,  # 结构化数据，按 tag 类型不同
}
```

**structured 字段按 tag 类型：**

- `api_request`: `{method, path, request_body, actor}`
- `api_response`: `{status_code, response_body, duration_ms}`
- `db_evidence`: `{table, column, value, business_keys: [[name, val]], sql}`
- `log`: `{trace_id, log_search_hint}`
- `replay`: `{available: bool, status_code, duration_ms, key_differences: []}`

### 数据提取映射表（从 finding 现有字段 → 证据步骤）

| 步骤 | tag | 数据来源（finding 字段） | 条件 |
| --- | --- | --- | --- |
| 规则来源 | rule | doc_refs[0].display_name 或 expected_behavior | 始终生成 |
| 接口请求 | api_request | har_evidence.method/path/actor + evidence.request_body | har_evidence 存在 |
| 接口响应 | api_response | har_evidence.status_code/response_body/duration_ms | har_evidence.status_code > 0 |
| 数据库证据 | db_evidence | 原始 title 正则解析 + source_entity + sql_verify | title 含 [DB] 或 source_entity 存在 |
| 日志线索 | log | investigation_guidance.trace_id + log_search | trace_id 或 log_search 非空 |
| 复现可用 | replay | repro_path 存在则标记 available=true | repro_path 非空 |
| 缺陷判定 | verdict | severity + risk_type + verdict/confirmation | 始终生成 |


### DB 证据解析（通用正则，不硬编码表名）

从原始 title（翻译前）解析 `[DB] table.col为负: biz_info（值=value）` 格式：

```python
db_match = re.match(r"^\[DB\]\s+(\w+)\.(\w+)为负:\s*(.+?)（值=(-?\d+)）", raw_title)
# → table, column, biz_info, value
# biz_info 进一步解析 "order_id=ORD-001, sku=PHONE-X1" → business_keys 列表
```

### 三视角差异化过滤（后端预计算，前端直接用）

后端在 `_format_single_finding()` 中为每个视角预计算过滤后的 evidence_chain：

- `evidence_chain_full`: 全部步骤（研发视角）
- `evidence_chain_business`: rule + verdict 步骤（业务视角）
- `evidence_chain_test`: rule + api_request + api_response + replay + verdict（测试视角）

### 证据完备度计算

基于 6 个证据维度计算完备度百分比：

1. 规则来源（有 doc_refs 或 expected）— 权重 15%
2. 接口请求（有 har_evidence.method/path）— 权重 20%
3. 接口响应（有 har_evidence.status_code > 0）— 权重 25%
4. 数据库证据（有 db_evidence 步骤）— 权重 15%
5. 日志线索（有 trace_id 或 log_search）— 权重 15%
6. 复现可用（有 repro_path）— 权重 10%

输出 `evidence_completeness: {score: int, dimensions: [{name, present: bool, weight}]}`

### 证据质量评分增强

`_compute_evidence_quality()` 新增维度：

- `has_api_response_evidence`: har_evidence.status_code > 0（+8 分）
- `has_db_evidence`: db_evidence 步骤存在（+6 分，替换原 has_db_signal 的粗粒度判断）
- `has_replay_capability`: repro_path 存在（+4 分）

## Implementation Notes

- **不修改 har_bridge/deep_verifier/replay_engine**：只在 formatter 层从已有字段提取，降低回归风险
- **向后兼容**：EvidenceStep 保留 label/content/detail 旧字段，新增 timestamp/source/confidence/structured 为可选字段
- **DB 标题解析用原始 title**：`_build_display_evidence_chain()` 接收的 finding 参数是翻译前的原始数据，可直接正则解析 `[DB]` 前缀
- **har_evidence.request_body 可能为空**：har_bridge 没有存 request_body（只存了 method/url/path/status_code/response_body/actor/duration_ms），需要从 evidence dict 或 har_evidence_list 补充
- **性能**：证据链构建是 O(1) 字段提取 + 最多 1 次正则匹配，无额外 IO，不影响响应时间
- **去除 slice(0,5) 截断**：EvidenceChain.tsx L148 `f.evidence_chain?.slice(0, 5)` 改为完整展示

## Architecture Design

```
原始 finding dict（含 har_evidence, source_entity, title, sql_verify, trace_id, doc_refs 等）
    │
    ▼
_build_display_evidence_chain(finding)  ← 重构：多源条件式提取
    │
    ├── step: rule        ← doc_refs / expected_behavior
    ├── step: api_request ← har_evidence.method/path/actor
    ├── step: api_response← har_evidence.status_code/response_body/duration_ms
    ├── step: db_evidence ← title 正则解析 + source_entity + sql_verify
    ├── step: log         ← trace_id + log_search
    ├── step: replay      ← repro_path 存在则标记
    └── step: verdict     ← severity + risk_type
    │
    ▼
evidence_chain_full (全量) + evidence_chain_business (过滤) + evidence_chain_test (过滤)
+ evidence_completeness (6维度完备度)
    │
    ▼
前端 EvidenceTimeline 渲染（按 tag 类型差异化展示结构化数据）
前端 EvidenceChain 三视角按预过滤链展示 + 完备度进度条
```

## 设计方案

证据链页面进行重大 UI 升级，核心目标是让企业用户一眼看到"这条缺陷有什么证据、还缺什么证据、每个证据的来源和内容是什么"。

### 页面结构优化

**证据卡片头部**（展开前）：

- 左侧严重度色条 + 标题 + 来源标签 + 时间戳
- 右侧新增：证据完备度迷你进度条（彩色环或条形，显示百分比+缺失数量）

**证据卡片展开后**（三视角 Tab 不变，内容重构）：

**业务视角**：

- 证据完备度卡片（6 维度 checklist，绿色✓/灰色✗，带权重百分比）
- 业务影响区（保持现有）
- 证据摘要（只展示 rule + verdict 步骤，简洁文字描述）

**测试视角**：

- 完整证据时间线（rule → api_request → api_response → db_evidence → replay → verdict）
- 每步展示结构化数据：接口请求显示 method+path+actor，接口响应显示 status_code badge + response_body 代码块 + 耗时
- 期望 vs 实际对比保持现有
- 复现按钮保持现有

**研发视角**：

- 全量证据时间线（含 log 步骤，展示 trace_id 和日志搜索命令）
- DB 证据步骤展示 SQL 代码块（带复制按钮）
- 接口响应步骤展示完整 response_body
- 调试信息面板保持现有

### EvidenceTimeline 组件重设计

每个证据步骤节点：

- 左侧：序号圆点（颜色按 tag 类型区分）+ 连接线
- 右侧：tag 标签 + 标签 + 来源标签 + 时间戳
- 内容区：按 tag 类型差异化渲染
- api_request: method+path 大字 + actor 标签 + request_body 代码块
- api_response: status_code 彩色 badge（2xx 绿/4xx 黄/5xx 红）+ response_body 折叠代码块 + 耗时
- db_evidence: 表名.列名 标签 + 业务主键列表 + SQL 代码块（带复制）
- log: trace_id 等宽字体 + 日志搜索命令代码块
- rule/verdict: 纯文本描述

### 证据完备度可视化

进度条 + 6 维度 checklist：

```
证据完备度 ████████░░ 75%
✓ 规则来源 (15%)  ✓ 接口请求 (20%)  ✓ 接口响应 (25%)
✗ 数据库证据 (15%)  ✓ 日志线索 (15%)  ✓ 复现可用 (10%)
```

缺失项用灰色+✗，已具备用绿色+✓，让企业一眼知道还缺什么。
