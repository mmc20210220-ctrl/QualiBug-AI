# Round 2: Capability Gap Resolver

## 问题
当前34+文件硬编码 `"plan_only"`，Phase93A-G管线已能检测 plan_only 状态并生成remediation action，但缺少一个统一的 Gap Resolver 来：
1. 精确定位每个 plan_only 假设的根因
2. 判断 gap 是否可自动解决、需客户配置、还是永久阻塞
3. 当条件满足时自动将 plan_only 转为可执行
4. 跨 scan run 追踪 gap 的开启/关闭状态

## 新建文件

### 1. `ai_test_asset_center/capability_gap_resolver.py` — 核心解析器
- **`GapRootCause`** enum: MISSING_BASE_URL, MISSING_AUTH, MISSING_OPENAPI, MISSING_TEST_ACCOUNTS, PRODUCTION_TARGET, SAFETY_BOUNDARY, BROWSER_DISABLED, TESTOPS_OFFLINE, WRITE_SANDBOX_MISSING, CLEANUP_MISSING, SNAPSHOT_MISSING, CONFIG_PLACEHOLDERS, DOCUMENT_GROUNDING, INTERACTIVE_AUTH_BLOCKER
- **`GapResolution`** enum: AUTO_RESOLVABLE, NEEDS_CUSTOMER_CONFIG, NEEDS_APPROVAL, NEEDS_INFRA, PERMANENTLY_BLOCKED
- **`CapabilityGap`** dataclass: root_cause, resolution_type, affected_families, affected_probe_count, config_task, validation_steps
- **`CapabilityGapResolver`** class:
  - `detect_gaps(preflight, capability_matrix)` → list[CapabilityGap]
  - `classify_gap(gap)` → GapResolution
  - `generate_config_tasks(gaps)` → list[ConfigTask] (what to configure, where, how to verify)
  - `auto_resolve(gap, context)` → ResolutionResult (try to auto-promote)
  - `build_gap_report(gaps)` → dict (for dashboard consumption)
- 复用现有的 `_capability_gap_counts()`, `ACTION_METADATA` 等模式

### 2. `ai_test_asset_center/gap_tracker.py` — Gap 状态追踪
- 跨 scan run 追踪每个 gap 的状态: open, in_progress, resolved, blocked
- 持久化到 `platform_outputs/_benchmark/gap_tracker.json`
- 检测 new gaps / resolved gaps / reopened gaps
- 纯 JSON，不做 HTML

### 3. `tests/test_capability_gap_resolver.py` — 测试
- 验证每种 root cause 被正确检测
- 验证 auto-resolve 逻辑
- 验证 gap tracker 状态转换

## 修改文件

### 4. `ai_test_asset_center/runtime_onboarding_remediation_kit.py`
- 集成 GapResolver：在生成 remediation actions 时同时写入 gap tracker
- 当 preflight 检查通过后，自动将对应 gap 标记为 resolved

### 5. `ai_test_asset_center/private_pilot_service.py`
- 在 scan preflight 流程中调用 GapResolver
- 当用户提供缺失配置后，自动重新评估并提升可执行的 plan_only 假设
- 在 scan 结果中输出 gap summary

## 设计原则
1. 复用现有管线：不替换 Phase93A-G，而是在其之上增加统一解析层
2. 行业无关：gap 检测逻辑基于通用 preflight check，不硬编码行业
3. 不造假：只有在 preflight 实际通过后才标记 resolved
4. 可观测：每个 gap 记录根因、影响范围、解决步骤
