# Frontend stack (source of truth)

This frontend is a **Vite + React SPA** — not Next.js. Stack: Vite 8, React 19, react-router 7. Dev server runs on port **5174** and proxies `/api` → backend `127.0.0.1:8088`.

- Primary customer journey is **Agent-first**, not module-first: `/dashboard` (New Task) → `/verify` (Live Workspace) → `/findings` (Agent Findings) → `/release` (Agent Decision). `/analyze` is the Knowledge / Understanding surface the Agent consumes. `/integration` and `/settings` remain supporting system surfaces. `/` redirects to `/dashboard` while preserving project/query context.
- `/dashboard` is **New Task / Agent Home**, not a KPI dashboard. Submitting a quality goal creates a real project-scoped backend Agent Task through `/api/v1/projects/{project}/agent-tasks`; task creation immediately performs a **read-only grounding evaluation** that may pin only an already-materialized Test Intelligence snapshot, select only source-backed Test Targets, and reuse the existing Scan Preflight authority. Task creation must never trigger a full enterprise-understanding rebuild, invent Test Targets, execute a Scan, or bypass Runtime Grounding/Preflight.
- The home interaction is an editable goal and explicit intent, followed by persisted task history from GET on the existing Agent Task collection. Suggestions populate a draft; only submit creates a task. Analysis and verification tasks both land in their task-bound `/verify` workspace. Task history is independent of project-result availability, scoped to tenant/project on the backend, and never reconstructed from browser storage or Campaign receipts. Project changes remount the task workspace to prevent cross-project state reuse. Project result failures remain visible and must not become zero Findings or prevent task/event inspection.
- The task workspace supports creation, inspection, regrounding, cancellation and explicit project-scope execution through the existing Task-to-Scan endpoint. Ready means preparation, not execution. Snapshot and binding diagnostics use progressive disclosure.
- Target selection records operator-requested task focus; it does not prove change impact or execution coverage. Knowledge may offer selection for a current pinned verify_changes task whose execution is not claimed. Rechecking conditions must preserve selected_test_targets. Actual project execution continues to use canonical Preflight and Scan governance.
- `/verify` is the **Live Workspace**. When a `task` query parameter is present it reads the persisted Agent Task and its backend Event Ledger. Task events are observable work events, not hidden chain-of-thought, and the frontend must never synthesize missing Agent events. `source_snapshot`, `selected_test_targets`, `runtime_grounding_status`, `grounding_blockers`, and `grounding_summary` come only from the Agent Task backend contract. A task-bound workspace must **not** call Test Intelligence to materialize/rebuild understanding; it renders the pinned target snapshot from the task. Existing Campaign/Finding/Release receipts must not be relabeled as Task events unless the backend ledger explicitly records them.
- Agent Task grounding is not execution. A task may be `BLOCKED` even when Scan Preflight is ready when selected Test Targets still have `NOT_GROUNDED` Action / Observer / Oracle bindings. A stale or missing persisted understanding snapshot is also a visible blocker; the frontend must not hide it by triggering a rebuild from the runtime path.
- Explicit project-scope execution posts to the task `/execute` endpoint and reuses the canonical Scan executor. Selected Test Targets remain context, not a claim of target-specific coverage. Semantic binding gaps do not automatically prohibit governed project experiments; current Scan Preflight, immutable source manifest and an existing knowledge version remain required. Analysis tasks never execute scans.
- Before execution is claimed, cancellation cancels only the orchestration record. After claim, cancellation requests a safe stop of the exact bound Scan lease; it never immediately labels the task cancelled. `execution_run_id` on this integration is the canonical Scan identity, not a separate ExecutionRun artifact. Lost leases show an uncertain recovery state with no automatic resubmission. Task completion reports orchestration completion, not verified Findings or release readiness.
- `/findings` is the Agent-first Findings surface: conclusion and business impact first, evidence inspection second. Only `isCustomerReadyFinding` results can be presented as confirmed problems. The historical management/list surface remains available at `/advanced-findings`; it is not a second truth source.
- `/release` is the Agent-first Decision surface: recommendation → why → next action. It reuses shared `deriveReleasePresentation` and real project-level `release_gate` / regression / pipeline facts. The detailed historical Gate surface remains available at `/release/details`; it is not a second release authority.
- `/analyze` is the unified Knowledge / Understanding workspace. It composes the existing Requirement Intelligence and Test Intelligence surfaces; it must not merge their truth semantics. Requirement readiness still comes only from the authenticated Requirement Intelligence API, while Test Target coverage still comes only from the authenticated Test Intelligence API.
- `/requirements` remains the backward-compatible Requirement Intelligence surface. Its readiness state must come only from the authenticated Requirement Intelligence API; generic scan status must not be presented as requirement readiness.
- `/test-intelligence` remains the backward-compatible Test Intelligence surface. Its coverage comes only from the authenticated Test Intelligence API. `COVERED` means current supported semantic units have evidence-backed Test Obligations; it is not total test completeness or execution coverage. Obligation state must remain `OBLIGATION_ONLY / NOT_MEASURED / NOT_EVALUATED` until the backend owns a real downstream execution contract.
- Requirement Intelligence and Test Intelligence workspaces must not display Bug Discovery run summaries as if they were product truth. The unified Knowledge workspace inherits the same boundary.
- `/advanced-dashboard`, `/advanced-findings`, `/release/details`, `/campaigns`, `/coverage`, `/jobs`, `/evidence`, `/requirements`, and `/test-intelligence` are advanced / compatibility surfaces. Do not re-promote these internal entities into first-level customer navigation unless the Agent-first product model is intentionally changed and this file is updated in the same change.
- Verify with `npm run lint`, `npm run typecheck`, and `npm run build` (includes `brand:check`) after changes.
- Honesty semantics are non-negotiable: never invent metrics or Agent activity on the frontend; missing backend data renders as 「后端暂未提供 / 未上报 / 待评估 / NOT_MEASURED」states, never as healthy-looking defaults.

## Task results and progressive disclosure

- Task workspaces default to an overview with next actions and artifact links. The URL `section` selects overview, deliverables, execution or activity; project/task context must survive switching and returning from Knowledge.
- Detailed task events, execution diagnostics and pinned targets appear only in their selected workspace. Technical task management and source evidence use explicit disclosure controls. Narrow screens use one content column.
- Knowledge offers requirement review and test design/data requirements through the existing Intelligence APIs. Shared project knowledge and historical project findings must never be labeled as task-specific completed deliverables. Structured data requirements are not materialized test data; target snapshots are not an executable test plan.
- Uploading additional sources is an explicit expandable action, not a required step when viewing existing results. Existing knowledge is reused; navigating result views must not create tasks or execute scans.

- Requirement review and test designs support local text/type filtering over their returned source-backed records. Filters never change canonical readiness/coverage counts. Lists paginate at 20 items, preserving selected task targets across pages and search. Requirement evidence is collapsed by default; understanding blockers are not presented as universal execution prohibitions.
- `view=test-data` is a presentation mode over the existing Test Intelligence response. It may summarize source-declared data requirements, preconditions and the exact `test_data_materialization_status`, but it must never invent concrete values or mark data usable without a backend materialization/validation receipt.
- Knowledge tabs mount on first visit and retain local filters, pagination and disclosure state while switching within the current page. Cached surfaces are scoped to project, task and source-upload revision; changing those remounts the surfaces. This UI state is not persisted knowledge or execution authority and does not survive leaving/reloading the page.
