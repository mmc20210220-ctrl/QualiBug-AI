## Syntax Check After Every Edit

**After ANY file edit (patch, write, terminal sed), always verify syntax before concluding the change succeeded.** A missing parenthesis, bracket, or quote is invisible in the diff but makes the entire module unimportable. Silent import failures cause background processes, cron jobs, and tests to die with zero output — and their exit code still reports "ok" to the scheduler.

Run immediately after editing any Python file:
```
python -c "import ast; ast.parse(open('path/to/file.py').read()); print('OK')"
```

Never skip this step. A "syntax OK" check takes 0.1 seconds and prevents hours of silent failures.

## One-off Artifact Convention (Repo-root Hygiene Boundary)

The repository root must stay clean: it holds only product code, configuration, and tracked release/test baselines.

- One-off debug scripts (`_*.py`) and run artifacts (`*.json`, `*.txt`, `*.log` outputs of scans, runs, probes, diagnostics) MUST be created in `.scratch/` (git-ignored), never in the repository root.
- Root-level patterns `/_*.py`, `/*.json`, `/_*.txt`, `/_*.log` and `/.scratch/` are ignored in `.gitignore`; the small set of tracked root JSON baselines consumed by product code, tests, or workflows is listed as explicit exceptions there. Do not add new root JSON files unless a tracked consumer reads them; otherwise place them in `.scratch/`.
- When a one-off script graduates into a durable tool, move it into `tools/` (or the owning package) with tests; never keep durable scripts at the root with a `_` prefix.
- Git history retains the migrated pre-cleanup artifacts; `.scratch/` is the local working area only and must never be committed.


1. Fail Fast / Errors Never Pass Silently：不要在代码里藏兜底逻辑来吞掉错误、隐藏问题。出了问题就应该让它爆出来，否则你永远找不到真实问题。
2. Fix the Cause, Not the Symptom / Don't Paper Over Bugs：当一个问题出现时，不要用各种 small fix、针对性补丁来掩盖它。必须定位真实根因，彻底修复。在 bug 上糊纸只会让系统积累你不知道的危险暗病。
3. Make It Observable：即使问题很难定位，也绝不要偷懒做表面修复。应该给项目增加充分的日志和可观测性，保证下次问题再现时你有足够信息去定位。问题无法修复时，只需要诚实告诉我信息不足、需新增日志，不要假装修好了。
4. Design for Debugging / Traceability：始终注意在关键路径上给自己留足排查日志，确保每一个关键节点都是可追溯的。
5. Living Documentation / Single Source of Truth：当项目关键技术栈或产品方向发生变更时，同步更新 agents.md。文档必须随代码一起演进，不能让它变成过时的谎言。

10.所有优化在现有模块基础上优化，不要重复造轮子，所有优化都要接入主链才算闭环，不要有断点

12.所有优化都要从根因上修复优化，换个陌生系统必须也要适用，否则就不算从根因修复优化

14.测试数据清理（cleanup / compensation / restore）是**测试完成后的 best-effort 环境卫生动作**，不是测试执行、Oracle 判定、Finding 真值、客户交付或回归统计的前置条件。对明确声明的非生产目标，只要测试实际执行且证据完整可复现，cleanup 失败、没有可用清理接口、无法逐条恢复、或存在测试数据残留，都只能作为独立的 cleanup/residue 状态和环境提示记录，绝不能把已执行测试改判为未执行/执行失败，绝不能把 Oracle 已确认的 VIOLATION 丢弃、降级或隐藏。能安全清理就 best-effort 清理；不能安全清理就不清理并明确记录残留，不要求每条测试数据完全回滚。生产环境和未声明环境仍然保持严格写入边界。
15.产品路线必须遵循**渐进理解 → 可证伪假设 → 真实执行 → 运行证据 → 更新理解 → 下一轮实验**。企业世界模型不需要、也不可能在测试前被完全、唯一、可证明地闭合；`UNKNOWN`、`AMBIGUOUS`、`PARTIAL`、`TECHNICAL_GROUNDING_PENDING` 等认识状态本身不能自动成为“不生成实验/不执行实验”的理由。只要目标是明确非生产环境、执行面和请求形状有真实依据、风险受控、实验可以被观察，就允许基于当前证据生成**待验证假设**并执行。真正需要 fail-closed 的是生产写入边界、未授权行为、凭据/敏感信息、不可控破坏风险，以及最终把某个结论作为真实 Bug/客户事实交付时的证据完整性；**认识上的不确定性不是安全失败，也不是执行失败。**
16.企业资料理解必须是**持久化、版本化、可增量演进的企业知识资产**，不是每次测试 Run 的临时前处理步骤。测试运行只能消费一个已存在并被明确 pin 的 `Enterprise Understanding Snapshot`；启动、重试、回归、重复或扩大一次测试 Campaign，本身绝不能触发全量资料重新解析、重新分块、重新 Embedding、重新调用 LLM 做企业理解、重新构建完整业务模型。只有源资料/连接器 revision、API/UI/DB schema、理解引擎版本，或运行时证据实际改变了相关知识时，才允许事件驱动地增量更新受影响的知识区域并产生新版本。**如果输入资料和理解引擎都没有变化，而一次新的 Run 仍导致全量企业资料重新进入解析或 LLM 理解流程，直接视为架构缺陷。**

## Enterprise Understanding Lifecycle Contract

**Enterprise comprehension and test execution have different lifecycles. The Enterprise Knowledge Center owns enterprise understanding; Test Run consumes it. A Run must never own or rebuild the enterprise model merely because testing is starting again.**

- **Persistent asset, not per-run computation.** Parsed documents, source-grounded facts, semantic candidates, entities, fields, actors, operations, state machines, rules, workflows, relationships, hypotheses, technical bindings, provenance, confidence/conflict state, and runtime-learned facts belong to a persistent enterprise-understanding asset. They survive individual scans and campaigns.
- **Every usable understanding state is versioned.** Each committed understanding snapshot must carry a stable version/identity plus the source revisions/fingerprints and understanding-engine/schema versions from which it was produced. Every Test Run must pin and record the exact understanding version it consumed, so two runs can be compared without confusing target-system change with nondeterministic re-understanding.
- **Content/revision addressing is the default invalidation mechanism.** Unchanged source content must not be reparsed or resent to an LLM. Source identity plus content hash/revision determine whether material changed; unchanged blocks, documents, schemas, and unaffected semantic regions are reused. A connector poll with no material revision must be effectively no-op for comprehension.
- **Incremental update is mandatory.** When a PRD chapter, API contract, DB schema, UI surface, connector resource, or other source changes, rebuild only the changed source regions and the knowledge subgraph that actually depends on them. Do not invalidate the full enterprise model merely because one source changed. Impact propagation must be explicit and receipted.
- **Runtime learning is a delta, not a full rebuild trigger.** Reproducible runtime evidence can confirm, weaken, split, conflict with, or invalidate existing knowledge. That evidence should create an understanding delta affecting the relevant entities/rules/bindings/hypotheses, then publish a new snapshot version. It must not automatically resend all enterprise material through the LLM.
- **Run lifecycle is read-mostly with respect to comprehension.** Starting `Run 2`, retrying a failed experiment, running regression, changing execution budgets, or repeating the same campaign must reuse the pinned understanding snapshot unless an explicit qualifying knowledge-change event occurred. Hypothesis/planning/execution/oracle work may vary per run; enterprise-material comprehension may not silently restart.
- **Allowed full re-comprehension events are explicit and exceptional:** initial enterprise onboarding; an operator-requested rebuild; a breaking understanding-model/schema migration; widespread source revision that invalidates most of the dependency graph; or a measured corruption/integrity failure showing the stored understanding asset cannot be trusted. A normal test run is never such an event.
- **Understanding-engine upgrades are migrations, not accidental Run side effects.** If parser/semantic/grounding/reasoning engine behavior changes materially, preserve the old snapshot and produce a new version through an explicit migration/rebuild process. Historical findings remain bound to the version used when they were generated.
- **LLM cost and latency are product constraints.** The high-cost comprehension pass belongs primarily to onboarding and true knowledge-change events. Steady-state repeated testing of an unchanged enterprise should incur near-zero document-comprehension LLM cost; ongoing LLM spend should be attributable to new/changed knowledge or run-specific reasoning, not redundant re-reading of the same enterprise corpus.
- **Idempotence acceptance rule:** with identical source fingerprints/revisions, identical understanding-engine/schema version, and no new runtime knowledge delta, invoking enterprise-understanding refresh must reuse the existing snapshot and must not produce semantically new work merely because a new scan/run id exists.
- **Architectural defect rule:** any path where `scan`, `run`, `retry`, `regression`, campaign creation, or execution scheduling implicitly calls full enterprise `parse → semantic extraction → LLM comprehension → model rebuild` on unchanged material is a lifecycle-ownership bug. Fix the ownership boundary; do not paper over it with a per-run response cache.
- **Current direction already has an incremental foundation and must converge on it.** Existing incremental semantic refresh behavior in the repository establishes the intended rule that changed sources are reparsed while unchanged materials remain untouched. Future work must make the whole test mainline consume that persistent asset consistently rather than creating a second comprehension lifecycle inside discovery execution.
- **Run-start freshness gate (P0-1, landed).** The connector sync path already drives `refresh_enterprise_business_knowledge_asset_incremental` via `connector_semantic_refresh` when a connector poll detects a `SOURCE_REVISION_CHANGED`. But manual/API re-uploads of source material updated the source occurrence `content_hash`/`remote_revision` *without* any such trigger, so `build_discovery_plan` silently consumed a stale understanding. Fix: `composition.load_enterprise_business_knowledge_asset_ensuring_current` (the Run-start entry) compares the persisted understanding's recorded `source_inventory` fingerprints against the current active source revisions; on drift it builds a `qualibug.source-change-refresh.v1` receipt and calls the **existing** incremental executor (source-scoped, no full re-parse), then consumes the refreshed snapshot. No drift → cheap load + fingerprint compare, zero LLM, zero re-parse (satisfies the no-op and LLM-cost rules above). Resettable via `QUALIBUG_UNDERSTANDING_AUTOREFRESH_DISABLED=1` (mirrors the `QUALIBUG_SEMANTIC_EXTRACTION_DISABLED` test kill-switch; default ENABLED). Detection guards: missing asset → caller does a normal full build; asset with no `source_inventory` baseline → no spurious refresh (pre-baked test assets unaffected). Verified by `.scratch/_verify_understanding_freshness_gate.py` (21/21).
- **Mainline Reasoner reuse gate (content-addressed, receipted).** The 11-engine Reasoner (`stage_reason_all_v2`) is the only mainline stage that re-invokes LLM comprehension on every run regardless of source revision. `discovery_runtime_planning.build_discovery_plan` therefore gates it on a content-addressed fingerprint of the full deterministic Reasoner input (raw PRD text + raw API text + projected world model from `project_knowledge_world_model` + model + temperature; provider/model identity via `ReasoningConfig.from_env`). When the fingerprint matches the persisted reuse state of a prior successful real execution, the LLM is skipped and the persisted hypotheses are replayed through the identical governed bridge (`hypothesis_slice_bridge.hypotheses_to_obligations`), and the mainline receipt is stamped `status="REUSED"` with the persisted run identity and a `fingerprint_receipt` (`hit|miss` + reason + sha256) so no new LLM comprehension is ever invisible. Reuse state lives at `platform_workspace/<project>/defect_discovery/mainline_reasoner_reuse_state.json` (`_utils._paths["reasoner_reuse"]`); it is written ONLY from a real execution whose meta status is `ok`/`empty` and records `run_id`/`campaign_id`/`strategy_fingerprint`. A degraded/failed/provider-unavailable run is never frozen as reusable state (next run re-invokes the LLM). Any input change — source text, knowledge asset (world model), model, temperature — misses automatically. Fail-open: missing/corrupt/foreign-schema state, or a read/write error, degrades to a fresh LLM run, never a wrong skip and never a crash. `QUALIBUG_MAINLINE_REASONER_REUSE_DISABLED=1` bypasses the gate for deterministic tests/debugging; the lower-level `QUALIBUG_SEMANTIC_CACHE_DIR` content-addressed response cache remains a separate optimization under the Reasoner itself.

## Non-Production Execution Contract

- QualiBug automatically performs read and write probes against explicitly declared non-production targets (local, development, test, QA, SIT, UAT, staging, pre-release, and sandbox). A source-bound campaign does not require per-probe manual approval.
- Production targets are a hard write boundary. Unknown or undeclared environment types are fail-closed for writes; never infer that an unknown target is safe.
- Every write must pass through the governed sandbox executor and emit before/after observations, cleanup/residue outcome, campaign/slice identity, target identity, and an audit receipt. Hidden seed/bootstrap writes outside this path are forbidden. A cleanup outcome may legitimately be cleaned, not attempted, unavailable, failed, or accepted residue according to the existing implementation contract; cleanup completion is not the authority for whether the test executed or whether its Oracle verdict is true.
- Multi-write scenarios must expose a per-write governance hook and emit one audit receipt per actual HTTP write. Never retry an entire scenario after any write may have been accepted. If a safe declared compensator exists, compensation is best-effort; compensation failure or absence is recorded separately and must not erase the original execution result or Oracle verdict.
- On explicitly declared non-production targets, the existence of a DELETE/compensating operation is **not a prerequisite for POST/PUT/PATCH execution**. If a safe source-declared cleanup path exists, use it best-effort; if it does not exist or cannot be proven safe, leave the test data in place and emit a visible residue notice. Do not block a valid test merely because every created/modified row cannot be restored exactly.
- Cleanup, compensation, rollback, restore, and residue handling are **post-test environment-management concerns**. They must never convert an already executed experiment into `NOT_EXECUTED`/execution failure, never convert a proven Oracle `VIOLATION` into indeterminate/pass, and never suppress a reproducible finding solely because test data could not be removed.
- Read-only mode remains available as an operator kill-switch, but it must block writes before any request is sent and report the blocking reason visibly.

## Enterprise Business Comprehension Contract

**This is the product's core discovery loop. Read it before proposing any discovery-capability work. The goal is not to prove the enterprise world model complete before testing; the goal is to continuously convert partial understanding into safe falsifiable experiments, then use real observations to deepen or correct that understanding.**

- The product's core competence is **progressive enterprise comprehension + evidence-driven falsification**. Enterprise materials, API/UI/DB structure, runtime observations, prior findings, and execution receipts jointly form the knowledge base. The system is expected to start from incomplete knowledge, generate bounded hypotheses, test them on explicitly declared non-production targets, and update the model from what actually happened. Deep understanding is an outcome of this loop as well as an input to it.
- **Understanding is not an execution-permission gate.** QualiBug MUST NOT require the entire enterprise model, every entity identity, every state transition, every field binding, every observer, or every business rule to be globally unique and fully grounded before any useful experiment may run. Local uncertainty may block only the experiment that genuinely depends on that unresolved coordinate; it must not freeze unrelated reachable experiments or the whole campaign.
- **Separate three authorities:** (1) `HYPOTHESIS_AUTHORITY` answers whether there is enough evidence to propose a testable possibility; it may be partial, inferred, conflicting, or runtime-derived. (2) `EXPERIMENT_AUTHORITY` answers whether the concrete operation can be executed safely and observably on the declared target; it requires real executable coordinates and safety governance, not complete business certainty. (3) `FINDING_AUTHORITY` answers whether the observed result is strong enough to assert a real Bug/customer fact; this remains strict and evidence-complete. A low-confidence hypothesis is allowed to become an experiment; it is **not** allowed to become a customer claim until runtime evidence proves it.
- **`UNKNOWN` is a diagnostic and exploration signal, not a default terminal state.** `UNKNOWN`, `AMBIGUOUS`, `PARTIAL`, missing written rules, or unresolved business semantics should first ask: “Is there a safe experiment that can distinguish the candidates or reveal the actual behavior?” If yes, generate that experiment and preserve the uncertainty in its lineage. Only when execution itself cannot be made concrete/safe/observable should the local path remain blocked.
- **Fail-closed is for safety and truth boundaries, not epistemic perfection.** Keep hard fail-closed behavior for production or undeclared targets, authorization boundaries, credentials/secrets, uncontrolled destructive writes, missing executable request coordinates, and final evidence claims. Do not use fail-closed semantics merely because the business model is incomplete, because two semantic candidates exist, because cleanup is unavailable, or because a written rule is absent when a governed runtime comparison can test the behavior.
- **Runtime evidence is allowed to correct the model.** A model decision is not immutable because it was produced earlier by parsing, grounding, Behavior IR, implementation binding, or governance. Reproducible runtime observations may confirm, weaken, split, conflict with, or invalidate prior semantic/binding hypotheses. Downstream code must not preserve an upstream guess merely to maintain pipeline consistency; the knowledge model must represent disagreement and revision explicitly.
- The final goal is **to find every bug in the enterprise system** — full depth and full breadth. Depth means reasoning through multi-step business causality, cross-entity state, and long-running lifecycle, not single-request assertions. Breadth means every operation, actor, state transition, invariant, and cross-system/cross-service/cross-database/cross-message-chain path, not a sampled subset. Anything that structurally caps depth or breadth is a defect in the harness, not an acceptable trade-off.
- **No limitation is acceptable by construction.** Fixed detector lists, closed bug-type taxonomies, capped hypothesis budgets, closed risk-family enumerations that silently coerce unknown families, and single-service assumptions are all prohibited as structural limits. Where a bound must exist for cost or safety, it must be an explicit, receipted, operator-visible budget with a named reason code — never a silent truncation and never a hidden default. A bound that cannot be seen in a receipt is a capability ceiling masquerading as a configuration value.
- The scope is **multi-system, multi-service, multi-database, multi-message-chain** enterprise topology, across all industries and all system types. A capability that only holds for one service, one datastore, or one synchronous request path is incomplete, not shipped.
- The verification layer must hold **regardless of who or what operates the system** — human operators, programs, or enterprise AI agents. Actor identity is an input to verification, never an assumption baked into a detector.
- Historical benchmark diagnosis has shown large first-loss at hypothesis-generation/business-comprehension stages, so comprehension remains an important bottleneck; however, this MUST NOT be interpreted as permission to add more parser/grounding/gating layers by default. A comprehension change is valuable only when it improves the conversion from source/runtime evidence → executable experiments → unique reproducible findings, or measurably recovers a diagnosed first-loss cluster without creating new blocking loss downstream.
- **All bug types are in scope, and the type list is open.** API, UI, business-process logic, performance, compatibility, and stability are examples, not an enumeration. Any defect in an enterprise business system is in scope: resource leaks, error-handling and recovery, configuration and deployment drift, data migration and schema evolution, observability gaps, localization, accessibility, availability, capacity and degradation behaviour, and classes that have no accepted name yet. A bug type must never be out of scope because the harness has no slot for it — that is a harness gap to close, not a boundary to document.
- **Bug-type reachability is a four-link chain, and every link is a potential ceiling.** To find a class of defect the product needs (1) an obligation/risk expression that can express the property or a hypothesis that can generate one, (2) an assertion/oracle that can state the observable violation, (3) an implemented observer that can measure the evidence on the right surface, and (4) an experiment protocol that can execute it. A class missing any one link is structurally unreachable no matter how deeply the business is understood. Any capability proposal that claims to add a new bug class must name what it adds at all four links, or say explicitly which link it leaves open.

- Closing a breadth gap does not license fabricated facts. **Formal findings remain evidence-backed, but hypotheses and experiments do not require prior business-rule proof.** Where written rules exist, preserve them as high-authority evidence. Where they do not, runtime-observation experiments may be generated from concrete system structure and observable behavior as long as the system does not invent request bodies, credentials, entity/table identities, SQL, or customer impact claims.
- Comprehension gains are still bound by evidence discipline, but evidence discipline must not be confused with “everything must be proven before testing.” A deeper hypothesis may enter the runtime-observation path as a labelled hypothesis when its executable coordinates are real and safe; only the resulting finding/customer statement must wait for reproducible observation evidence.
- **Runtime observation is a first-class evidence source (source-grounded includes runtime-observed).** Enterprise source material is never complete and can itself be wrong; implicit rules and implicit semantics surface only at runtime. Therefore a finding's evidence basis may be **runtime-observed behavior** (controlled two-arm comparison: the permitted actor succeeds while a prohibited actor also succeeds; an illegal state transition; a conservation break; a leak) — reproducible under a governed experiment, receipted, with the cleanup/residue outcome recorded independently — **without any written source rule for it**. Cleanup completion is not part of defect truth: inability to remove or perfectly restore test data must never block, downgrade, or erase a reproducible violation. Written rules remain the highest-precision binding channel where they exist, but their absence must not block discovery: it must degrade the obligation to the runtime-observation channel (receipted as such), never silently drop it. This does NOT license inference as fact: the product still never invents request bodies, credentials, business rules, table names, SQL, or impact — it tests what it can concretely execute and observe. Runtime-observed evidence also feeds finding matching signals (actor role + operation + violation shape + reproduction), so defects whose rule never appears in any document remain findable and matchable. **Source attribution is "attribute when present, never fabricate":** a finding whose obligation bound written rules MUST carry their source references (document + locator + statement); a finding with no written source (implicit rule, hidden semantics, or a purely runtime-discovered defect) carries its runtime evidence (observed actor / operation / violation shape / reproduction) as the basis and is a fully valid bug — no fabricated source is ever attached, and absence of a written source never downgrades or blocks a reproduced, evidence-complete defect.
- **Source-backed business-rule semantic extraction (shadow + augment phases):** the extractor layer split (frozen regex candidate layer vs. open-semantic LLM recall), deterministic evidence validation, runtime modes, the unified rule candidate ledger, and the SPEC §19 promotion gates are implementation anchors of `ai_test_asset_center/AGENTS.md` (Enterprise Comprehension — Implementation Anchors). Only `rule_origin=explicit` candidates may ever enter formal rule governance; inferred candidates remain hypotheses until runtime evidence or explicit source authority upgrades them.
- **Product complexity must earn its existence.** When two layers repeatedly re-resolve the same entity/field/actor/operation identity, or when a new governance gate primarily creates `BLOCKED`/`INDETERMINATE` outcomes without improving externally measured defect discovery or safety, treat that as architecture debt. Prefer one canonical authority, fewer re-interpretation points, and end-to-end survival of evidence over adding another adapter/gate. The product is successful when unfamiliar systems yield more unique reproducible Bugs with less target-specific work — not when the repository contains more mechanisms.

## Brand Direction Contract

- QualiBug AI is enterprise software behavior-space infrastructure. It maps actors, states, data, rules, and real execution trajectories into a computable, verifiable, evolvable behavior-space model. The long-term direction is to become the independent verification layer (Enterprise Behavior Layer) for enterprise-system operations in the AI era — whether performed by humans, programs, or enterprise AI agents. The target is all industries and all system types: manufacturing ERP/MES/WMS is only a beachhead market, never a product boundary, and no capability may be scoped to it. Enterprise understanding is a persistent, versioned, incremental knowledge asset that outlives any individual Test Run; the product discovery loop is **partial understanding → falsifiable hypothesis → governed real execution → observation → model delta → next snapshot / next experiment**. It must never require a supposedly complete enterprise model before learning from the system itself, and it must never rebuild unchanged enterprise understanding merely because another test run starts. Bug discovery is open-ended by design: bug types (API, UI, performance, authorization, conservation, concurrency, …) are post-hoc classification labels for reporting and regression only — discovery itself is driven by business invariants, testable hypotheses, runtime observations, and system-space coordinate changes, and must never be capped by a fixed detector list or a closed bug-type taxonomy. Any evidenced violation of a business invariant or reproducible runtime property is in scope, including types that have no name yet.
- The governed Behavior Field mark is the brand source of truth: Q is the enterprise-system boundary, the plane is behavior space, nodes are states, and the curve is an observed behavior trajectory.
- The login radar is an approved decorative metaphor for enterprise-system behavior observation; it is not a product-health signal and is not part of the governed logo geometry.
- Brand and decorative product visuals use no insect, crawler, spider-web, or scraping semantics; insect, crawler, spider-web, and scraping semantics remain prohibited. `Bug` means a verified divergence between observed and expected behavior.
- Decorative brand motion must never represent actual system health, provider health, campaign health, scan health, model health, evaluator health, or commercial readiness.
- Brand work remains industry-neutral, preserves existing product copy unless separately approved, and keeps frontend 5174 and backend 8088.
