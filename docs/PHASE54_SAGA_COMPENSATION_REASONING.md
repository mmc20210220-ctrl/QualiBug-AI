# Phase54：Saga 补偿与回滚完整性反例引擎

## 解决的问题

企业系统最难发现的一类事故，通常不发生在“创建订单”或“调用退款”这一个接口，而发生在失败后的最终收敛：订单取消了但钱没退、库存仍冻结；重试时退款做了两次；业务状态显示已回滚但 Saga 长期停在 `running`；补偿任务不断重试却没有进入失败或人工处置。

Phase54 将主业务单据、补偿/退款/冲正记录、残留副作用和 Saga/工作流实例构造成可执行的只读 Oracle。它不把 `HTTP 200` 当作结果正确，而是验证失败或取消后的**最终业务事实是否完整、幂等、可追溯、金额正确且真正收敛**。

## 可发现的缺陷

- **补偿缺失**：订单、支付、审批、预订等进入取消/失败/回滚状态，但没有完成态退款、释放、冲正或补偿记录。
- **重复补偿**：同一业务主单产生多条完成态退款、释放、冲正或回滚结果。
- **补偿金额错误**：退款/冲正总额与原单、可退金额或配置口径不一致，包含超补和少补。
- **补偿孤儿数据**：退款、补偿、释放记录指向不存在的订单、支付单、预约单或审批单。
- **残留副作用**：业务已取消/失败，但库存仍预占、支付授权仍有效、额度仍冻结、权益仍生效。
- **Saga 未收敛**：业务已进入回滚触发状态，对应工作流仍处于 `running`/`processing`，没有进入 `compensated`、`cancelled` 等允许终态。
- **补偿超时**：待补偿、重试中或处理中任务超过企业 SLA 仍未结束。

## 配置方式

引擎会从 OpenAPI 中保守识别 `refund`、`rollback`、`compensation`、`release`、`reversal` 等可读取集合，并根据外键形状推导基础可追溯/重复补偿关系。

对于真实企业系统，建议在 `business_saga_compensation_reasoning.contracts` 显式配置：

- 主实体与补偿实体的 GET 路径；
- 业务主键和补偿外键；
- 取消/失败/回滚触发状态；
- 补偿成功、待处理、Saga 终态和残留副作用活跃状态；
- 金额字段、金额关系、容差与补偿 SLA；
- 库存预占、支付授权、权益/额度等残留资源集合。

完整示例见 `examples/business_saga_compensation_reasoning_config.example.json`。

## 安全边界

- `safe_live` 只执行 GET，分页读取均有上限；不会退款、取消、重试、回滚、释放库存或修改 Saga。
- 补偿重试、强制回滚、取消竞态、重复消息消费只生成 `sandbox_required` 任务，必须在隔离环境审批执行。
- 证据只保存接口路径、字段名、统计量与业务身份哈希，不保存原始订单、退款单、token 或 header。
- 同一反例跨运行持续出现会提高置信度；仍需要人工确认后才回灌企业缺陷模式库。

## 价值

它让 QualiBug 从“发现接口异常”升级为验证**失败路径是否真正闭环**。该能力适用于支付、退款、库存预占、预约、审批、积分、优惠券、权益、ERP 同步和任何采用 Saga / 补偿事务的企业系统，专门覆盖资损、库存冻结、重复扣/退、对账差异和长时间卡单等高影响问题。
