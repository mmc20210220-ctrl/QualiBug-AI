## 2. 量化成功标准（双方共识的"及格线"）

POC 结束时，满足以下全部条件即为成功：

| # | 标准 | 成功线 |
|---|---|---|
| S1 | 接入时长：从提供环境访问权到产出首份缺陷报告 | ≤ 【1】个工作日 |
| S2 | 发现真实缺陷：经客户方确认的有效缺陷数量 | ≥ 【10】个，其中 P0/P1 ≥ 【3】个 |
| S3 | 证据完整率：S2 中每条缺陷附完整证据链（请求/响应/前后状态） | 100% |
| S4 | 误报控制：客户判定为误报的比例 | ≤ 【20】% |
| S5 | 价值复盘：出具 POC 价值报告（缺陷清单 + 证据 + 折算成本） | 完成 |

**"客户确认"的定义**：客户技术对接人在缺陷清单上逐条标记"有效 / 误报 / 存疑"，标记响应时效 ≤ 2 个工作日；超时未标记的条目按"存疑"计，**不计入** S2 成绩。

## 3. POC 节奏表

| 时间 | 里程碑 | 客户方必须到场的人 |
|---|---|---|
| D1 | 环境接入 + 首次扫描启动 | 技术对接人 |
| D3 | 首份缺陷报告交付，逐条过 | 技术对接人 |
| W2 末 | 中期对齐会：展示中期战果、校准剩余范围 | 技术对接人 + 决策者 |
| W4 末 | 价值复盘会：对照本协议第 2 节逐条验收 + ROI 报告 + 商务方案 | **决策者必须到场** |

## 4. 双方责任

**客户提供**：目标环境访问地址与测试账号；必要的业务资料（接口文档/操作手册，有什么给什么，没有也能做）；缺陷确认的及时反馈。

**QualiBug 提供**：部署与接入；每周进展简报；POC 价值报告；全程技术支持。

**边界声明**：POC 期间 QualiBug 仅对第 1 节声明的非生产环境执行读写探测；每次写操作经治理沙箱执行，附前后观测与清理回执；客户可随时要求切换为只读模式。

## 5. 成功后的商务路径

POC 验收成功即进入商务流程：按《QualiBug 定价模型》出正式报价；**POC 费用（如收取）可 100% 抵扣首年合同**。

### 使用要点（内部）

1. **S2 的数值谈判**：客户想压低成功线是好信号（说明在意结果），守住"P0/P1 ≥ 3"下限——这是价值证明的核心。
2. **决策者到场是硬条件**：W2 中期会如果决策者不到，主动改期，不要妥协成"只和技术过一遍"。
3. **"存疑不计入"是双向诚实**：我们不用存疑凑数，客户也不能用拖延标记来否认成果——写进协议对双方都是保护。
4. 本模板与 `pricing-model.md` 配套使用；异议应对见 `objection-handling.md`。
