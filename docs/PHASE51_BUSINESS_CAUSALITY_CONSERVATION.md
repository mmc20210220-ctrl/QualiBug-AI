# Phase51：业务副作用与守恒反例引擎

## 要解决的问题

企业线上最危险的一类问题，往往不是某个接口报错，而是每个接口都返回 `200`，但一次业务动作的最终事实已经断裂：

- 订单显示已支付，却没有支付流水、发票、库存预占或审批结果；
- 同一订单重复产生两笔付款、两次库存扣减、两张发票或多条台账；
- 支付、退款、审批、库存、台账记录引用了不存在的主单；
- 主单金额与支付/退款/发票金额之和不一致；
- 订单总额与小计、税额、运费、优惠等组成字段不守恒。

Phase51 将这些关系建模为可执行的业务 Oracle，而不是把“支付重复”“金额错误”作为固定 Bug 名称匹配。

## Oracle 家族

1. **因果完整性**
   - 达成特定状态的主实体必须产生必要副作用。
   - 例：`status=paid` 的订单至少拥有一条支付流水。

2. **副作用幂等性**
   - 一次性业务动作的副作用数量不能超过配置上限。
   - 例：同一退款单不得产生两次退款流水。

3. **副作用可追溯性**
   - 每条支付、库存、审批、台账、发票等记录必须能关联到真实主实体。
   - 仅当主/从集合在有限分页内完整读取时判定，避免因数据截断制造误报。

4. **跨实体金额守恒**
   - 主单金额与关联副作用金额之和必须一致。
   - 支持容差，避免货币舍入误报。

5. **单据内金额守恒**
   - `total = subtotal + tax + shipping + fee - discount - coupon` 等可配置公式。
   - OpenAPI 中字段语义足够清晰时会自动推导；关键财务口径建议显式配置。

## 自动推导与企业配置

引擎会从 OpenAPI 列表接口中识别：

- 主业务主键：如 `order_id`、`invoice_no`；
- 依赖外键：如 `payment.order_id`；
- 业务状态：如 `status`、`state`；
- 金额字段：如 `total_amount`、`amount`；
- 支付、退款、库存、审批、台账、发票、物流等副作用资源名。

当名称或金额口径有歧义时，使用 `examples/business_causality_conservation_config.example.json` 显式锁定契约。显式配置优先于自动推导。

## 安全边界

- `safe_live` 仅发送 GET 请求。
- 主单与副作用集合的分页读取有页数、记录数和响应体上限。
- 重放提交、重复回调、并发消费等写验证仅生成 `sandbox_required` 计划，不会触碰企业生产数据。
- 证据只保存字段名、汇总数字和业务身份哈希，不保存原始业务行或认证凭证。
- 发现默认 `needs_human_review`；相同反例跨运行重复出现时才提高置信度。

## 示例：发现“接口正常但业务已错”

当 `/orders` 和 `/payments` 都返回 `200` 时，引擎仍可发现：

- `paid` 订单缺少支付流水；
- 一个订单拥有两条支付流水；
- 订单金额 `20`，关联支付金额之和为 `19`；
- 支付流水关联了不存在的订单；
- 订单 `total_amount=80`，而 `subtotal=70 + tax=10 - discount=5`，真实应为 `75`。

这些都直接进入主缺陷报告、风险排序、发布阻断候选与跨运行证据记忆。
