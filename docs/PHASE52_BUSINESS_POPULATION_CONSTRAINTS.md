# Phase52：跨记录业务约束与群体反例引擎

## 解决的问题

很多企业 Bug 的每一条记录都“看起来正确”，问题只会在一组业务记录放在一起时暴露：

- 客户把一笔 10,000 元的限额拆成多笔订单，单笔都通过但日累计已超额；
- 同一会议室、车辆、员工、库存资源在同一时间段被重复占用；
- 批量导入/同步任务显示完成，但 `processed + pending` 不等于总数，或成功与失败统计无法闭合；
- 同一客户、商品、日期等复合业务事实被写成多条不同 ID 的记录；
- 高金额报销、采购、退款、授信等绕过审批门槛。

Phase52 的目标不是匹配“订单超额”“预约冲突”这些 Bug 名称，而是从多个有效记录共同必须遵守的业务关系中寻找可证伪反例。

## 可执行 Oracle

1. **群体额度/配额**
   - 按客户、租户、账户、部门、SKU、仓库等主体聚合数量或金额。
   - 支持按天、月、年、小时或固定秒级窗口。
   - 只有观测值已经超过阈值时才报警；数据不完整不会被误判为合规。

2. **时间区间与容量冲突**
   - 同一房间、人员、设备、车辆、班次、授权、库存资源的有效区间不得超过允许并发数。
   - 对于重复预订、双重分配、授权重叠等问题，GET-only 的事实快照即可发现。

3. **复合业务键唯一**
   - 检查 `customer_id + plan_id + effective_date`、`employee_id + shift_date + shift_code` 等逻辑主键。
   - 解决“数据库 surrogate id 唯一，但真实业务事实重复”的漏检。

4. **批次终态完整性**
   - 批量导入、导出、同步、迁移、异步任务在终态时必须满足：
     - `processed == total`
     - `success + failed == total`
     - `success + failed == processed`
   - 能发现任务接口 200/完成，但内部丢数据、漏处理、重复统计的问题。

5. **审批阈值门禁**
   - 金额达到阈值的业务必须拥有允许的审批状态或审批凭据。
   - 后端事实检查，不依赖前端流程是否展示审批按钮。

## 推导与配置

引擎会从 OpenAPI 识别资源集合、主键、常见主体字段、起止时间、批次统计字段和审批字段；对区间冲突、批次完整性可保守自动推导。

额度、审批阈值、复合业务键的真实口径通常具有企业特性，建议在 `business_population_constraints.contracts` 中显式配置。示例见：

`examples/business_population_constraints_config.example.json`

## 安全边界

- `safe_live` 只发 GET 请求。
- 证据只写入字段名、聚合值、窗口、以及业务身份哈希；不保存原始业务行、token 或 header。
- 拆单绕过、并发预订、竞态审批等需要写入的验证只生成 `sandbox_required` 计划。
- 所有发现保持 `needs_human_review`，跨运行重复出现时才提高置信度。

## 价值

该层把“单记录校验”升级为“群体业务事实校验”。它能直接抓到接口各自返回正常、单条数据也合法，但累计额度、排班资源、批处理结果或内控审批已经错误的生产级缺陷。
